## Stage A — exception and badge-capture stability

### A1. Protect unread badge scanning from a stalled native capture

- Check `IsHungAppWindow` before calling `PrintWindow`.
- Bound the awaiting scan path to 3 seconds.
- Keep one in-flight capture per HWND/PID pair; a timed-out native call is not started again while its original worker remains active.
- Apply a 15-second retry cooldown after timeout or an unresponsive-window result.
- Treat timeout, hung, skipped, and unavailable captures as unknown/unavailable, never as “no unread”; do not clear an existing badge based on them.
- Keep the existing badge recognition, confidence, notification, and two-scan clear-confirmation policies unchanged.

**Important limitation:** `Task.WaitAsync` bounds the caller but cannot cancel a native `PrintWindow` call already running. The worker remains isolated and gated until it returns. A hard termination boundary would require a separate helper process and is explicitly out of scope for this stage.

### A2. Complete exception isolation at asynchronous UI/background entry points

- Guard window startup and periodic scan timer entry points with the existing `GuardedRunner`.
- Guard both button and Enter-key unlock paths.
- Catch and report exceptions in the delayed Shell window-reconcile callback.
- Add a final catch-all to the single-client exit event so unexpected exceptions do not escape an `async void` handler.
- Preserve existing specialized handling and reporting for other handlers that already have complete catches.

### A3. Regression coverage

- BadgeProbe: verify per-window in-flight exclusion, cooldown behavior, and PID isolation.
- RegressionProbe: verify GuardedRunner reports action failures, contains reporter failures, and leaves successful actions successful.
- CI: Release build, BadgeProbe, ArchitectureProbe, RegressionProbe, typography validation, and the PR test-package workflow.

## Acceptance checklist

1. Build the application and all probes in Release on Windows x64.
2. BadgeProbe and RegressionProbe pass.
3. No unread state is cleared after a timed-out, hung, skipped, or unavailable capture.
4. A stalled capture for one client does not prevent the dispatcher from processing other UI work or the scan loop from moving on after the soft timeout.
5. No duplicate capture is launched for the same HWND/PID while the original native call remains in flight.
6. Existing notification rules, per-account identity guards, WhatsApp hosting, lock-screen behavior, and 100%/200% cold-start DPI behavior remain unchanged.
7. User real-device regression: two WeChat accounts plus one WhatsApp, normal unread changes, a temporarily unresponsive client, client recovery, and both supported cold-start DPI settings.

## Explicit non-goals for this stage

- No changes to the exit strategy (graceful close vs. forced termination).
- No changes to WeChat profile/database extraction or temporary plaintext storage.
- No Named Pipe security redesign.
- No mouse-hook lifecycle redesign.
- No runtime DPI switching support.
- No stable merge or official release.


## Stage B — graceful client exit with safe Kill fallback

### B1. Request graceful close first

- Use the original, already-validated client HWND and post `WM_CLOSE`; do not synchronously send a window message from the WPF dispatcher.
- Single-client exit and “全部退出” use the same `ExitBatchService` lifecycle.
- Start all unique-PID graceful requests before waiting on any client, so a slow client cannot serialize the batch.
- A failed or late graceful request is not reported as a successful exit and does not authorize Kill by itself.

### B2. Bounded grace period

- Give each client 2.5 seconds to exit after the graceful request.
- Wait for all graceful-exit results concurrently.
- Bound graceful-request and Kill-request workers to 3 seconds; confirm process exit after Kill for up to 3 seconds.
- Start all eligible Kill requests before waiting for any Kill confirmation.

### B3. Revalidate process identity before Kill

- Capture the original process wrapper, PID, UTC start-time ticks, and HWND before requesting close.
- Before graceful close and again before Kill, verify that the PID still resolves to the same process generation.
- Verify the original HWND still belongs to that PID whenever the HWND remains valid. If the HWND was destroyed by the graceful close, the captured process start time remains the process-generation guard; if the handle is still valid but belongs to another PID, abort.
- Never use `Kill(entireProcessTree: true)`; only the validated client process may be terminated.

### B4. Safe Kill fallback and honest result reporting

- If the process remains alive after the grace period, revalidate identity and then call `Kill(entireProcessTree: false)`.
- If identity cannot be verified, do not Kill. If a request or confirmation times out, preserve the account entry and report the result as unconfirmed.
- Distinguish normal exit from forced exit in diagnostics and status feedback.

### Stage B regression coverage

- RegressionProbe covers graceful success without Kill, Kill fallback, identity mismatch blocking Kill, Kill failure, Kill timeout, and duplicate-PID de-duplication.
- ArchitectureProbe covers concurrent request ordering, bounded request timeout, partial failures, and unconfirmed exit results.
- Keep the existing exit-choice reentrancy and deferred JNest close behavior unchanged.

### Stage B explicit non-goals

- No changes to window hosting/restoration, WeChat identity binding, WhatsApp hosting, unread recognition/notification rules, lock-screen behavior, or Named Pipe/database/mouse-hook security.
- No stable merge, official Release, or replacement of the v2.0.0 stable baseline.


## Stage C + D — combined hardening preview (v2.0.2-beta.3)

Base: `maintenance/v2.0.2-stage-b` (Draft PR #65). Implementation:
`maintenance/v2.0.2-stage-cd` (stacked Draft PR). No merge or stable Release.

### C — local profile scratch database

- Continue using the existing current-user/SYSTEM-only directory ACL and owner/process-generation cleanup.
- Reject a reparse-point scratch directory *or its immediate parent*. After applying
  the explicit DACL, **read back** owner, access-rule protection, and allowed SIDs
  before writing any decrypted SQLite copy.
- Refuse to create a new plaintext file if its JNest creator process start time
  is unavailable; this avoids unidentifiable copies that cannot be safely reaped.
- Cleanup ignores reparse-point directories/files and unknown `contact-*`
  filenames, especially under the shared legacy temporary directory.
- Preserve original data extraction, SQLCipher verification, and WAL merge logic.

### C — single-instance Named Pipe

- Set `PipeOptions.CurrentUserOnly` on both server and client connections.
- Enforce a maximum of 2,048 characters per newline-delimited activation
  frame. Reject control characters, partial frames, and malformed UTF-8.
- Apply a 3-second per-connection read deadline so a local peer cannot hold
  the sole server instance open indefinitely.
- Cap pending activations before the WPF main window loads to 16 requests.
- Same-user clients remain within the user's security boundary. This does
  not cryptographically authenticate every command against malicious
  processes *already running as the same Windows user*.

### D — window monitoring

- Retain the existing Win32 enumeration and 5-second fallback, Shell event
  filtering, async scan lock, account identity checks, and 100%/200% cold-start
  behavior. No change to HWND matching or window role detection.
- Prune stale per-PID process-name/version metadata opportunistically and cap
  caches at 256/128 entries, preventing accumulation from unrelated processes.

### D — diagnostics

- Retain existing 10-MB per-file rotation, 50-MB total cap, and 7-day retention.
- Throttle identical error fingerprints to one entry per 30 seconds, retaining
  the first error and distinct failures; cap the fingerprint table at 256.

### D — global low-level mouse hook

- Use a detachable named timer handler instead of accumulating anonymous
  `Tick` subscriptions.
- Catch all managed exceptions at `WH_MOUSE_LL` callback boundary, pass
  mouse input through on failure, and queue diagnostic I/O outside the hook.
- Check `UnhookWindowsHookEx`: if it fails, retain the managed callback
  delegate so a still-active native hook cannot call a garbage-collected delegate.
- Keep the current modal-click shield and caption-block region geometry.

### Automated and manual gates

- ArchitectureProbe: bounded same-user pipe transport and malformed messages,
  scratch ACL/readback and cleanup filtering, metadata cache eviction, and
  repeated-error throttle.
- Continue Build Check, BadgeProbe, RegressionProbe, typography validation, and
  both Windows x64 publish modes.
- Real Windows test: two WeChat accounts plus WhatsApp at 100%/200% cold starts,
  toast/second-launch activation, account metadata and avatar fallback, normal
  unread badges, repeated modal dialogs, mouse input outside JNest, and 50-MB
  diagnostic retention.

### Unchanged/out of scope

- No new native injection or WeChat/WhatsApp APIs, profile extraction heuristic,
  active process ownership algorithm, runtime DPI switching, unverified forced
  exit, merging stacked PRs, or official Release.


## v2.0.2-beta.4 — consolidated review remediations

  stale HWND throttle state when a window is detached, forgotten, invalid or
  the host is disposed. Keep global WinEvent hooks and the 1-second safety

  names, cached avatars and the existing profile-read privacy protections.

  supported Node.js 24 action generations.
- Retain modal/lock, unread capture, privacy permissions, no forced
  HWND reparenting, no dynamic DPI compatibility promise, and no stable merge.
